# Vigilo v0.2.1 evaluation report

**Result:** the release candidate detected all 10 scripted repetitions in each of the three immediate-tier chains. The 60-second benign-activity window produced no alerts. The resource and storage measurements are coarse container measurements; they are not production-host benchmarks.

## Test subject and method

The daemon image was rebuilt from implementation commit `d6c9ebcff284be5ba955c528681822fc5c178a2d` and run with the dedicated `eval/docker/docker-compose.yml` stack. The stack uses an isolated Docker bridge, a daemon container with its own filesystem and process namespace, and an in-network webhook listener. It does not use the production compose file, mount host `/proc` or `/home`, or send the scripted outbound probes to the public internet.

The eval suite uses real filesystem writes and TCP connections inside the daemon container. File notifications are event-driven; suspicious-port detection is sampled from `/proc/net/tcp` at a configured one-second interval. The latency runner now refuses to write medians unless all 10 expected observations are successfully paired for each chain.

## Results

| Measurement | n / window | Result |
|---|---:|---:|
| Keystore write-to-webhook latency | 10 | median 83.6 ms; p95 245.4 ms |
| `.env` write-to-webhook latency | 10 | median 26.9 ms; p95 48.9 ms |
| Suspicious outbound connect-to-webhook latency | 10 | median 570.8 ms; p95 1075.5 ms; one-second polling |
| Alerts during benign development activity | 60 seconds | 0 |
| Idle container CPU / memory | 30 one-second samples | median 0.18% CPU / 13.94 MiB |
| Trigger-load container CPU / memory | load window, one-second samples | median 1.85% CPU / 15.44 MiB |
| Event-store growth after copied-store WAL checkpoint | 30 events; one 4096-byte page | 4096 B total, or 137 +/- 137 B/event at page resolution |

The storage estimate's uncertainty equals the estimate: SQLite grew by one page for 30 events. Treat 137 +/- 137 B/event as a rough order of magnitude, not a byte-accurate rate. The resource figures come from `docker stats` for the container, not daemon RSS or a systemd service on a validator.

## Scope and limitations

- The false-positive result is zero alerts in this specific 60-second in-container development workload, with suppression tuning disabled. It does not establish a daily or production-signer rate.
- The latency chains cover filesystem writes and sampled suspicious-port connections. They do not measure create, remove, rename, default five-second polling, sustained load, or maximum event throughput.
- The analyst/LLM tier was not exercised. This run says nothing about model detection accuracy, prompt-injection resistance, API availability, or cost.
- OrbStack/macOS hosts a Linux container here. This is development evidence, not release acceptance on a real Linux validator, and it does not cover NVIDIA/GPU or production network conditions.
- The test cannot establish coverage against direct execution paths that bypass the collector, root-level tampering, filesystem reads without auditd, or event loss under a burst large enough to overflow inotify's queue.

## Reproduction

From `eval/`, install the locked test dependencies with `uv sync --extra dev`, start the dedicated stack with `docker compose -f docker/docker-compose.yml up -d --build --force-recreate`, then run:

```sh
uv run pytest -q
uv run python scripts/run_evaluation.py
uv run python scripts/run_overhead.py
```

The measurement JSON is generated under the ignored `eval/results/` directory. This report records the release-candidate values so they remain reviewable with the source.
